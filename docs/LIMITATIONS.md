# 边界与原因

写下来是为了避免"看起来像 bug，其实是设计"的反复提问。

## 1. 没有逐字流式输出

**现象**：`stream=True` 能拿到合法 SSE，但事件几乎在同一时刻全部到达。

**原因**：WBIPC 的 `http.fetch` 是请求-响应式的，没有流式原语。上游 SSE 会在桌面端被
整段缓冲，桥接拿到的是完整字符串，再拆成事件回放。

**代价**：首字延迟 = 整段生成时间。几百字的回答无感，几千字会明显停顿。

**能不能改成真流式**：不能，除非改 WorkBuddy 的管道协议（不在本项目范围内）。

## 2. 单次响应体有硬上限

**现象**：让它输出很长的内容，失败并返回 `E_PAYLOAD_TOO_LARGE`。

**原因**：桌面端 `readBodyCapped` 对响应体有硬编码上限（约 640 KiB）。

**影响范围**：常规对话、代码补全、工具调用都在安全区内；一次性输出上万行会撞墙。
拆成多轮对话即可绕过。

**为什么仓库不提供"解除上限"的补丁**：那需要改写 `app.asar`、重算头部完整性哈希、
并覆盖 `WorkBuddy.exe` 里内嵌的整档校验值——会破坏 Authenticode 签名，属于修改厂商软件、
绕过其完整性保护，违反 EULA，也可能触及著作权法里的技术措施条款。这个项目不做，也不提供脚本。

## 3. 桌面端必须在运行

桥接不是 WorkBuddy 的替代品，是它的"外挂入口"。桌面端退出 → 管道消失 → 请求 503。
桥接会在**请求到来时**尝试拉起一次（120 秒冷却），但不会定时轮询拉起——
用户主动关掉的应用不该被反复弹出来。

## 4. 仅 Windows

依赖 Windows 命名管道（`\\.\pipe\...`）。没有跨平台计划。

## 5. 模型清单依赖桌面端产品配置

清单来自 `acc-product-config-v3.json`。文件不可读 → 清单为空 → 桥接明确报错而不是给过期表。
这让 `doctor.py` 的第 1、2 步成为排障起点。

## 6. 积分只走一条通道

桥接不发第二份计费请求，也没有本地缓存/复用回答。你看到的扣费就是桌面端自己会扣的量。
但要注意：**重试策略会避免重复扣费**——只有"确定没发出去"的失败才重试一次，超时一律不重试。

## 7. 不做多账号 / 不做轮询池

一个桥接实例绑定**一个**已登录的桌面端。要切换账号，切桌面端登录态即可。
本项目不实现账号池、自动换号、额度分摊——那既脆弱，也更容易被判定为滥用。

国内版和国际版同时用**不属于**这一类：它们是两个独立安装、两份独立订阅、两套登录态，
由 `setup.py` 各起一个进程、各占一个端口（18490 / 18491）。一个实例永远不会在
两个积分池之间调度——那是「换号」，不是「多实例」。

## 8. 响应中的 usage 可能为 0

上游并非所有分片都带 usage；聚合时缺失会补成
`{"prompt_tokens":0,"completion_tokens":0,"total_tokens":0}`。
计费以桌面端为准，不要拿桥接返回的 usage 做成本核算。
